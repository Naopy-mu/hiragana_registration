# 研究用 筆跡収集アプリ

日本語・スマホ向けのFastAPIアプリです。参加者は説明に同意して参加者IDを受け取り、記入用紙PDFをダウンロード・印刷し、記入した用紙の写真を提出します。研究者はPDF・元写真・補正PNG・対応表CSVを選んでZIPで回収し、配布用PDFの複数登録・選択も研究者画面から行えます。

本番構成は **Azure App Service（Linux）＋Supabase PostgreSQL＋非公開Storage** です。2026年11月14日にAzureへ初回公開し、本番設定でのDB接続・研究者ログイン・配布PDF取得を確認しました。詳細は[検証記録](docs/VERIFICATION.md)を参照してください。

## ローカルで開く

Python 3.12を使用します。プロジェクトフォルダのPowerShellで実行してください。`python`がWindowsストアのエイリアスの場合は、最初の行を`py -3.12 -m venv .venv`へ置き換えます。

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe scripts/bootstrap.py
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

- 参加者画面：<http://127.0.0.1:8000>
- 研究者画面：<http://127.0.0.1:8000/researcher>
- ローカル用研究者パスワード：`data/local-researcher-password.txt`

初回の`bootstrap.py`はランダムな秘密値を含む`.env`を作成します。既存`.env`は変更しません。ローカルモードはSQLiteと`data/`内の非公開ファイル保存を使うため、外部アカウントなしで操作できます。`.env`、DB、提出画像はGitやデプロイZIPへ含めません。

同じWi-Fiのスマホから確認する場合は、PCの`ipconfig`でIPv4アドレスを調べます。例えば`192.168.1.20`なら`.env`を`APP_BASE_URL=http://192.168.1.20:8000`、`ALLOWED_HOSTS=localhost,127.0.0.1,testserver,192.168.1.20`へ変更し、`--host 0.0.0.0`で起動します。スマホでは`http://192.168.1.20:8000`を開きます。Windowsが接続確認を表示した場合は、利用するプライベートネットワークの接続を許可してください。

## 参加者の操作

1. 研究説明を読み、同意して登録します。氏名・メールアドレスの入力はありません。参加者IDと専用の再開リンクが表示されるので、リンクを保存します。
2. ①・②…のボタンから、記入するPDFを保存します。初期用紙の`hiragana_collection_a4.pdf`はA4・8ページです。A4・実際のサイズ（100%）・片面で印刷し、氏名などの個人情報を書かずに記入します。
3. 記入した用紙を1枚ずつ撮影するか、撮影済み画像を複数選択します。撮影・選択後に「続けて撮影／続けて選ぶ」で写真を追加できます。用紙の端・四隅の黒丸・QRが写真内へ収まるようにします。順番は任意です。
4. 写真がそろったら「まとめて登録」を押し、認識ページ・補正プレビュー・登録状況を確認します。同じQRを登録すると差し替えの確認が出ます。読取・補正・新しい画像の保存がすべて成功してから置き換えます。
5. PDFごとの「①を提出する」「②を提出する」で個別に提出します。すべての写真を登録する必要はありません。未登録のページには、参加登録時の同じ原本PDFの該当ページを未記入のまま、元の位置に入れます。写真0枚でも全ページを未記入テンプレートで提出できます。確定前に未記入ページ数を確認します。提出後も写真を追加・撮り直して登録できます。登録時は写真だけを保存し、以前の提出PDFは保持します。「追加分を提出する」を押すと、未記入だったページや撮り直したページを新しい写真に差し替えて提出します。他の提出済みページはそのまま残し、複数PDFでは選んだ用紙の追加分だけを反映します。用紙が1つの場合は「提出する」を使います。

再開リンクには本人のデータへアクセスする鍵が含まれます。参加者同士で共有しないでください。鍵はURLの`#`以降に置き、APIではBearerヘッダーで送るため通常のURLアクセスログへ入りません。参加者IDだけではアクセスできません。

同意日時・同意本文・同意文の版をDBへ保存します。連打や通信再試行は同じ登録キーを使い、DBの一意制約で二重登録を防ぎます。番号はDBが発行するため同時登録でも重複しません。欠番は再利用しません。

写真の一覧では、送信前の拡大確認と削除ができます。「まとめて登録」で1枚ずつ処理し、結果を写真ごとに表示します。一部が失敗しても残りを処理し、再試行では未登録の写真だけを送ります。差し替えを見送った写真は再送しません。未登録の写真がある間は提出を無効にします。

上記の提出制限は、写真一覧に追加したまま未送信の写真が残っている間だけです。用紙のページ自体が未登録でも提出できます。未記入テンプレートは提出PDFへ差し込み、元写真や補正PNGの記録は作りません。個別の提出PDFは`P001_01.pdf`・`P001_02.pdf`のような名前で取得でき、すべての用紙を提出した場合は全体をまとめた`P001.pdf`も取得できます。

登録前の写真はブラウザのメモリだけに保持し、ページを閉じたり再読み込みすると消えます。再開リンクで復元できるのは登録済みの写真です。「まとめて登録」を押すまでは写真0枚のIDの自動削除判定にも数えません。

## 写真を登録しないIDの自動削除

登録から24時間以上経過しても写真が0枚の未提出IDは、Supabase Cronが毎時確認して削除します。写真が1枚以上あるID、提出済みID、PDFや提出日時が記録されているIDは対象外です。1回の処理は最大1000件で、保存中の行は次回へ回します。Azureが休止していても、Supabase DB側で処理します。

一部のPDFだけを未記入で提出した場合も、最初の提出日時を保存するため自動削除の対象外です。

削除したIDの再開リンクは無効になります。再度参加する場合は研究説明への同意からやり直し、新しいIDを発行します。古い登録要求の再試行で以前のリンクが復活するのを防ぐため、登録キー・トークンのハッシュだけを`expired_registrations`に保持します。同意本文や参加者IDはこの表へ残しません。写真や配布用紙のStorageファイルをこの処理で削除することはありません。

設定は`migrations/003_expire_empty_participants.sql`で作成し、`migrations/004_schedule_empty_participant_cleanup.sql`で毎時ジョブを登録します。現在のSupabase環境には両方を適用済みです。詳細・停止方法は[Azure手順](docs/AZURE.md)を参照してください。

## 研究者の回収操作

研究者画面へログインすると、参加者ID・登録日時・提出状況・登録ページ数に加え、提出した用紙数と未記入ページ数を確認できます。対象者を「提出のある全員」または個別選択、種類を「PDF・元写真・補正済みPNG・対応表CSV」から複数選び、ZIPで取得します。一部の用紙だけを提出した人も回収でき、PDFは提出済みの用紙分を収録します。すべての用紙が提出済みの場合は結合PDFも収録します。未提出者の元写真・補正PNGも個別選択で回収できます。

対応表CSVには参加者ID・QR・ページ番号・元写真名・補正PNG名・提出PDF名に加え、用紙番号・用紙名・用紙内のページ番号・`page_status`を含めます。`submitted`は写真を提出済み、`blank`は写真未登録のページを未記入テンプレートで補って提出済み、`registered`は写真登録済みで未提出、`not_registered`は未登録・未提出です。追加・撮り直し分も、提出前は`registered`として提出PDF名を空欄にします。元写真・補正PNGは現在の登録画像、PDFは最後に確定した提出内容を回収します。互換性のためCSVの値`blank`とAPI・DBの`blank_*`の名称を維持します。`blank`の行は元写真名・補正PNG名を空欄にします。研究者向けAPIでもサーバーが認証を確認します。

## 研究者画面でPDFを複数登録し、配布対象を選ぶ

1. `/researcher`へログインし、「配布用紙の管理」を開きます。現在の配布対象、合計ページ数、提出順とQRを確認できます。
2. 「PDFを追加」で原本を複数選び、「PDFを登録」を押します。全ページのA4寸法・QR・四隅の黒丸を検証して保管します。登録するだけでは配布対象は変わりません。登録済みPDFは一覧の「PDF確認」でダウンロードできます。
3. 一覧のチェックボックスで、記入・提出してもらうPDFを1件以上選びます。複数選択でき、選んだ順に①・②…となります。同時に配布するPDF間でQRが重複すると区別できないため、理由を表示してその組み合わせを拒否します。
4. 「選択したPDFを配布する」を押して確定します。新規参加者には、選んだPDFそれぞれのダウンロード・提出ボタンとページ一覧を表示します。各PDFを独立して提出でき、写真がないページは同じ原本PDFの未記入テンプレートで補います。結合PDFは選んだファイル順・各ファイルのページ順で作成します。

**選択の変更は新規登録する参加者から適用します。登録済みの参加者は、登録時のPDF・QR・ページ順・必要一覧を継続します。** 配布対象から外してもPDFは登録一覧に残り、あとで選び直せます。記入途中のデータや過去の提出が新しい用紙へ混ざることはありません。

登録する原本PDFは1ファイルあたり500ページまで、25MB以内です。全ページのA4寸法・QR・四隅の黒丸を確認します。

PDFのQRは[ZXing-C++](https://github.com/zxing-cpp/zxing-cpp/tree/v3.1.1/wrappers/python)で読み取り、通常の200dpiで読めないページだけ400・600dpiで原本から再描画します。OpenCVによる読み取りも補助として使います。小さく情報量の多いQRに対応し、高解像度で得た位置は補正用の座標へ変換します。ページ内の複数QR・不正な文字・回転・四隅不足は、引き続き拒否します。

アップロードしたPDFと設定は版ごとにDBと非公開Storageへ保存します。サーバー再起動やAzure再デプロイ後も、確定した配布版を維持します。複数の研究者画面が同時に操作した場合は、後から古い画面で上書きしないよう競合を検出します。通信が途切れた場合は現在の配布版を再確認し、同じ確定操作を安全に再試行できます。

この操作に環境変数変更・コード編集・再デプロイは不要です。同意文を変更する操作は含めていません。

## 原本と初期設定

提供された原本は`resources/worksheets/hiragana_collection_a4.pdf`にそのまま保存しています。全8ページのQRは原本から実際に読み取り、順番は`HIRA1-01`〜`HIRA1-08`です。A4上の黒丸中心は左上からmm単位で`(10,10)`・`(200,10)`・`(200,287)`・`(10,287)`です。ページ順・QR・補正座標を`config/pages.study.json`へ記録しています。

`PAGE_CONFIG=config/pages.study.json`は、新しいDBを初期化するときの設定です。初期化後の配布版はDBで管理するため、ファイルを書き換えるだけでは配布版は切り替わりません。通常の変更は研究者画面から行ってください。

同意文は提供いただいた本文で、版は`2026-11-10-v1`です。`config/pages.test.json`と`resources/worksheets/test-worksheet.pdf`は自動テスト用の3ページ構成で、`TEST-02`・`TEST-03`は開発専用の架空コードです。実際の配布原本の続きや総ページ数を推測したものではありません。

初期設定の`worksheet.path`は`resources/worksheets/`内のPDFを指定します。配布PDFは静的ファイルとして公開せず、参加者や研究者の認証を通したAPIで取得します。本番は正式原本・校正済みの設定・確定済み同意文が必要で、テスト用紙設定のままでは起動しません。

画像処理はQRと四隅の黒丸から用紙外枠を推定し、写真内に収まるかを確認してA4へ射影補正します。向きをそろえ、グレースケールと滑らかな背景補正を使い、二値化した画像を保存しません。読取不能、対象外QR、四隅不足、端切れ、強い影、ぼけは理由を表示します。JPEG・PNG・WebPを使用できます。HEICはJPEGへ変換して選択してください。

## 撮影時のフラッシュ

「カメラで撮影」では画面全体に映像を表示し、下中央の丸いシャッターで撮影します。対応端末では初期状態でフラッシュをオンにします。右上の⚡を押すと「フラッシュをオフにしますか？」と確認し、「オフにする」を選んだ場合だけ消灯します。「オンのまま」や確認画面でのEscapeではオンを維持します。オフからオンへ戻すときは確認なしで切り替わります。閉じるボタンや常時表示の説明文は撮影画面に表示せず、スマホの「戻る」またはEscapeで撮影を中止できます。撮影用ライトだけを操作できる端末では、オンの場合に撮影中だけライトを点灯します。

同じページで続けて撮影する間は、許可済みのカメラ接続を再利用します。写真の確認中は映像を無効にしてプレビューを外し、ライトも消灯します。撮影を中止したとき、ページを離れたとき、タブやアプリを切り替えたとき、提出完了時、または撮影後5分間使わなかったときは接続を終了します。ブラウザ自体の許可設定は変更しないため、初回・再読み込み後などに許可が必要になる場合はあります。

ブラウザや端末が発光制御に対応しない場合は、フラッシュアイコンを灰色・斜線付きで表示し、ライトなしで撮影できます。撮影できない場合は参加者画面へ戻り、エラーを表示します。スマホのカメラアプリでフラッシュをオンにして撮影し、「撮影済み画像を選ぶ」から登録することもできます。フラッシュ制御の可否は実行時に判定し、iPhone・Androidの全機種で自動発光を保証するものではありません。プレビューは画面を満たすよう拡大し、撮影画像はカメラの範囲全体を保存します。用紙全体を画面内へ入れ、撮影後は補正プレビューで光の反射による文字の欠けがないか確認してください。

## 研究者パスワード

```powershell
.\.venv\Scripts\python.exe scripts/set_password.py
```

12文字以上のパスワードを2回入力します。出力された`RESEARCHER_PASSWORD_HASH='...'`を`.env`へ設定して再起動してください。Azureには右辺の外側の引用符を除いたハッシュを設定します。平文は保存せず、ソルト付きPBKDF2ハッシュをサーバーで照合します。

研究者セッションは8時間です。`SESSION_SECRET`を変更すると既存の研究者セッションを無効にできます。参加者リンクの再試行用の`PARTICIPANT_TOKEN_SECRET`は別の値を使い、収集期間中に変更しません。両方とも32文字以上のランダム値を設定し、秘密値はブラウザやGitへ渡しません。

## Supabaseへ接続する

1. [Supabase Dashboard](https://supabase.com/dashboard)で研究用プロジェクトを作成し、DBパスワードを保管します。
2. **SQL Editor → New query**で001・002・003のSQLを順に実行し、`migrations/005_individual_worksheet_submissions.sql`でPDF別の提出テーブルを追加します。既存環境には未適用のものだけを実行します。003は期限切れ登録の管理と削除関数を追加します。自動削除を有効にする場合は、004で毎時ジョブを登録します。現在のSupabase環境には001〜005を適用済みです。
3. **Storage**で`handwriting-private`を開き、**Public bucketがオフ**か確認します。別名を使う場合は非公開バケットを作成し、環境変数も変更します。サイズ制限は元写真の上限25 MBと全ページPDFの大きさを許容する値にし、公開・匿名アクセスポリシーは追加しません。
4. **Connect → Session pooler**の接続URLをコピーします。IPv4で利用できる5432番ポートを使い、`postgresql://`を`postgresql+psycopg://`へ変更し、`?sslmode=require`を付けます。DBパスワードの記号はURLエンコードしてください。
5. **Project Settings → API Keys**のサーバー用Secret key（`sb_secret_...`）を取得し、`SUPABASE_SECRET_KEY`へ設定します。旧JWT形式の`service_role`を使う場合だけ、代わりに`SUPABASE_SERVICE_ROLE_KEY`へ設定します。
6. `.env`へ`BACKEND_MODE=supabase`、`DATABASE_URL`、`SUPABASE_URL`、秘密鍵、バケット名を設定し、再起動して別の参加者で提出・回収を確認します。

旧バージョンのDBを引き継ぐ更新では、002適用後の初回起動は**以前の`PAGE_CONFIG`を維持**し、既存参加者を以前の用紙版へ紐付けます。その後、研究者画面から正式原本を確認・確定し、`PAGE_CONFIG`を`config/pages.study.json`へ変更します。以前の用紙がテスト設定なら、この切り替えは開発モードで行ってから本番へ移します。本番ではDB内の現在版も検証し、テスト版が配布中のままだと起動しません。今回のローカル環境では、この移行と正式原本の適用を実施済みです。

Supabaseの[接続方法](https://supabase.com/docs/guides/database/connecting-to-postgres)、[非公開バケット](https://supabase.com/docs/guides/storage/buckets/fundamentals)、[APIキー](https://supabase.com/docs/guides/getting-started/api-keys)に基づく構成です。サーバー秘密鍵はサーバー環境変数にだけ設定します。

## 保存・再試行

元写真・補正PNG・提出PDF・配布用紙PDFは非公開Storage、各保存先と状態はDBで管理します。「提出ID＋QR」「提出ID＋用紙ID」は一意です。提出時は参加者行をロックし、登録済み写真と参加登録時の原本PDFの未記入ページからのPDF生成・Storage保存が成功してから、その用紙を提出済みにします。失敗時はその操作を取り消し、すでに提出した別の用紙を保持して再試行できます。

差し替え画像と配布用紙は毎回別の保存先へ書き込み、途中失敗で以前のファイルを壊しません。追加写真の登録は、元写真と補正PNGの保存だけを行います。提出時は以前のPDFの未変更ページを再利用して追加・撮り直し分だけを反映し、個別PDFと必要な結合PDFを保存してから、DBの参照をまとめて更新します。結合PDFには確定した個別PDFだけを使い、他の用紙の提出待ち写真を混ぜません。PDF生成や保存に失敗した場合も、以前の提出PDFと登録済み写真を保持して再提出できます。参加者の初回提出日時は維持し、各用紙の提出日時は再提出の完了時刻へ更新します。DB更新の応答だけ失われた場合は、保存ファイルを保持し、状態確認と再試行で回復します。配布用紙の旧版は既存参加者のために保持します。

提出待ちは、写真の現在の版と最後に提出した版を比較して判定します。登録日時と提出日時が同じ場合や、サーバー間で時計に差がある場合も、追加写真を提出PDFへ反映できます。版の記録はPDFの保存と同じトランザクションで確定し、既存データは日時と未記入QR一覧で判定します。DB列の追加は不要です。画面でも提出後の状態を確認し、同じ写真が未提出・未記入のまま残る場合は再試行を案内します。

## テスト

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

テストは一時DBと一時保存先を使い、順不同の登録・PDF内のページ順・差し替え・未記入テンプレートによる補完・個別提出・QR失敗・同時操作・認証・選択ZIP・保存障害を確認します。配布用紙の登録と配布選択の分離、旧参加者の版維持、追加写真の登録と提出の分離、過去のPDFを使った追加提出、他の用紙の提出待ち写真の除外、再起動後の保持も検証します。

複数PDFの登録・配布選択を実ブラウザで再実行する場合は、検証専用サーバーを別のターミナルで起動します。毎回新しい一時DB・保存先を使い、Supabaseへ接続しません。Windowsではインストール済みGoogle Chromeを使います。

```powershell
npm.cmd install --prefix .browser-tools --no-save --package-lock=false playwright
# 別ターミナルで起動したままにする
.\.venv\Scripts\python.exe scripts/serve_library_browser_test.py
# 元のターミナルで実行する
node tests/browser_library.cjs
```

`tests/browser_e2e.cjs`と`scripts/verify_local.py`は初期の3ページテスト設定を前提とした検証補助です。実際の8ページ収集環境へテスト用写真を送らないでください。依存関係の直接の版は`requirements.txt`、検証時の全依存関係は`requirements.lock.txt`に記録しています。[検証記録](docs/VERIFICATION.md)も参照してください。

写真の一括登録・模擬カメラ・期限切れからの復帰は、ローカルの検証用サーバー（`http://127.0.0.1:8001`）を起動してから、`node tests/browser_batch.cjs`・`node tests/browser_camera.cjs`・`node tests/browser_expiry.cjs`で確認できます。これらはAPIとカメラを模擬し、実際の参加者データを作成しません。サーバーの起動設定は[検証記録](docs/VERIFICATION.md)を参照してください。

個別提出の実ブラウザ検証は、同じ検証専用サーバーを使って`$env:BROWSER_BASE_URL='http://127.0.0.1:8002'; node tests/browser_submissions.cjs`で実行できます。検証用の複数PDFを登録するため、本番URLでは実行できません。`python scripts/verify_individual_submissions_postgres.py`は、`.env`の接続先の検証専用スキーマを作成して同時提出と005を確認し、終了時にそのスキーマだけを削除します。

Supabaseの実接続とAzureへの初回公開は確認済みです。公開URLでのスマホ実機撮影・全8ページの提出・研究者回収の通し確認は、これから実施します。

## 公開するときに行う操作

| 開く場所 | 入力・実行するもの |
| --- | --- |
| ローカル研究者画面 | PDFを複数登録し、配布対象をチェックして確定 |
| Supabase SQL Editor | 001〜003・005のマイグレーションを実行し、非公開バケットを確認。004で写真0枚のIDの自動削除を有効化 |
| ローカルPowerShell | `scripts/set_password.py`で本番パスワードハッシュを生成。`python -c "import secrets; print(secrets.token_urlsafe(48))"`を2回実行して別々の秘密鍵を生成 |
| Azure Portal／PowerShell | [Azure手順](docs/AZURE.md)に従い、Web App作成・環境変数登録・ZIPデプロイ・HTTPS確認 |
| 公開したスマホ画面 | 同意→原本PDF取得→印刷・記入→撮影→提出→研究者回収まで確認 |

提供原本・同意文・Supabase接続・Azure本番環境の初期設定は済んでいます。別環境へ公開する場合は、その環境用の接続情報と本番専用の秘密値を用意してください。
